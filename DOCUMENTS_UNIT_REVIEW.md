### High

- **A scan can be saved without the scan-review confirmation by labeling it manual.** The regular scan UI gates Save, and the create route checks `reviewed === true` when `source === 'scan'`. But `source` is client supplied, and anything other than `'scan'` defaults to `'manual'`. A client can take the suggestion returned by `/scan`, POST those values as a manual document, and get reminders without the confirmation. The database check only requires `reviewed_at` for rows labeled `scan`; it cannot tell where manual fields came from. See [DocumentForm.jsx](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/web/src/components/documents/DocumentForm.jsx:205>), [documents.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/routes/documents.js:255>), and [schema.sql](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/db/schema.sql:357>).
  
  **Ruling:** the normal UI requires a tick; “always enforced” by the server and database is too strong. Add a scan-specific commit flow, bound to the user’s pending suggestion, and keep manual entry separate. No software can prove that a person truly read a field, but the scan flow should not let its own result be committed through the manual path.

- **The user sends an identity-document image to a third party.** The page says the image is sent to “the AI service,” before the Read action, which is useful disclosure. It does not identify the active provider or separately call out passports and other identity documents. The prompt’s instruction not to return names or numbers does not prevent the provider from receiving the original image. Provider terms also matter: current Groq documentation says inference inputs and outputs are not retained by default, but permits temporary retention for reliability or abuse monitoring; Anthropic’s current API retention guidance says inputs and outputs are generally deleted within 30 days, subject to exceptions. These terms can change. [Groq data controls](https://console.groq.com/docs/your-data), [Anthropic retention guidance](https://privacy.anthropic.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data).

  **Ruling:** the notice is a start, not enough for real use. Before enabling scans for users, choose the provider and review its applicable terms and retention controls; show the provider by name; add a separate, explicit acknowledgement before sending identity documents; and update the privacy policy to describe the provider transfer, retention, and what LifeAdmin stores. Offer manual entry at that point. Whether to prohibit identity scans until those decisions are made is the owner’s decision; I recommend disabling them until then.

### Medium

- **One broad tick is a weak check for a deadline-setting workflow.** It says the person compared the name and dates, and the fields remain editable, but there is no separate confirmation of the expiry date. A mistaken expiry can create a missed deadline. I would require a distinct acknowledgement for the expiry date, and for the issue date when it affects the validity check. Requiring people to type dates twice is optional friction, not proof that the date is correct.

The likely worst result is a wrong kind or date, or hostile text in an allowed output field. The schema still permits arbitrary title and issuer strings, and `checkedSuggestion` truncates them but does not remove names or numbers. - **PDF validation is explicitly heuristic, not sanitization.** The code checks header, EOF, and selected action names in raw bytes; it acknowledges that names may be hidden in compressed object streams. `Content-Disposition: attachment`, `nosniff`, CSP sandbox, and owner-only retrieval are good protections against the site rendering a stored PDF in its own origin. They do not make the downloaded file safe for other viewers. Scanning reads only page one, which can miss the expiry on another page; the UI does disclose this. See [documents.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/routes/documents.js:94>) and [DocumentForm.jsx](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/web/src/components/documents/DocumentForm.jsx:31>).

For the first public version, I recommend keeping that scan path but storing the resulting image rather than the original PDF. Attachment-only is a sensible origin-isolation measure, but the blacklist should not be presented as proving a PDF is safe.
- **pdf.js is current, but still parses hostile input in the user’s browser.** `6.4.299` is the current release listed by Mozilla’s release page, and the lockfile pins it exactly; the manifest uses a caret range. The implementation disables eval support and XFA, uses a worker, loads library assets from this site, and fetches them only when a PDF is chosen. Those are good choices. Self-hosting avoids a runtime third-party script request, but does not remove the parser attack surface or the npm/build supply chain. The selected PDF is read wholly into browser memory; `disableAutoFetch` does not bound parsing of supplied bytes. Add client-side byte and resource limits before public use, and keep the dependency under regular security updates. [Mozilla PDF.js releases](https://github.com/mozilla/pdf.js/releases), [PDF.js API options](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html).
- **File access and limits are reasonably scoped, with operational costs.** Files are read through authenticated routes, selected by both file and document IDs and `owner_id`; responses are private/no-store, `nosniff`, and sandboxed. The global advisory transaction lock protects the aggregate ceiling against concurrent additions, assuming the route transaction and PostgreSQL behavior work as intended. The ceilings are 1 MB per image, 2 MB per PDF, two files per document, 20 MB per person, 200 MB total. The base64 column uses about one-third more space than the file bytes, and the limit does not bound backup memory: export holds rows in memory and the command serializes the whole backup into one JSON string. See [documents.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/routes/documents.js:153>), [schema.sql](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/db/schema.sql:373>), and [backup.cjs](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/scripts/backup.cjs:18>).
- **`reference` is sensitive free text stored in clear.** A user is likely to put a passport, policy, or plate number there. It is returned by the API and included in the backup. Since it is not required for reminders, my initial-release ruling is to remove it. If the owner keeps it, encrypt it with a managed key and treat document files and backups as part of the same sensitive-data design; encrypting only this column would be incomplete.
- **Renewal planning looks correct by inspection.** Planner rows are keyed by expiry occurrence and reminder rule. Changing the expiry replans the document, cancels obsolete pending rows, and creates rows for the new expiry. Sent rows remain historical; a reminder already delivered for the old expiry is not retracted. The worker rechecks whether the exact occurrence is still wanted before sending. See [reminders.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/lib/reminders.js:248>), [reminders.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/lib/reminders.js:317>), and [reminderWorker.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/lib/reminderWorker.js:94>).
- **The Unit 5 push lease is safer, but its timeout is not a wall-clock deadline.** Each attempt gets its own claim, and a stale holder cannot overwrite the newer holder’s outcome. The `web-push` timeout is a socket inactivity timeout; its documentation explicitly says a response that keeps sending packets can exceed that duration. So the two-minute lease can still expire during an active send, allowing an at-least-once duplicate. The documented duplicate boundary is an acceptable tradeoff only if the code does not claim that every send is guaranteed to stop within eight seconds. [web-push timeout documentation](https://www.npmjs.com/package/web-push).
- **Login counting closes the simultaneous pre-check gap, but is not equivalent to counting only failures under a per-key lock.** A right password resets the entire limiter row. If it overlaps wrong attempts that have already incremented that row, the reset can erase their counts. Also, once the limit is reached, even a correct password is refused without verification. The reported concurrency test supports the basic burst case, not these interleavings. See [auth.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/routes/auth.js:73>) and [ratelimit.js](</C:/Users/Promotech/OneDrive/Desktop/claude projects/LifeAdmin-main/src/lib/ratelimit.js:41>).

## B. Rulings

**Unit 5 decisions**

- Thrown delivery errors now count toward the three-attempt limit on the ordinary path. The ambiguous case where a provider accepted a push but the database did not record it remains inherently at-least-once.
- Claim tokens prevent stale outcome writes. Duplicate sends after lease expiry are an accepted limitation, but the eight-second socket timeout is not a strict maximum duration.
- Task notifications are rechecked against current task access at send time.
- The named bill-paid and task-update handlers were already transactional; the member-add and ownership-transfer handlers are now transactional. Backup table and shape metadata are now read within the snapshot transaction.
- The consume-first login change is a useful burst limiter, but **not equivalent** to the earlier rule of counting failures only and resetting only the successful try. Keep the HMAC privacy boundary; replace whole-row reset behavior with a concurrency-safe per-attempt reservation/refund or other design that does not erase concurrent failures.

**Documents decisions**

- The ordinary scan UI requires confirmation, but the API/database enforcement is bypassable by submitting the suggestion as `source: 'manual'`. Fix before treating “always reviewed” as an invariant.
- One checkbox is better than silent save, but expiry deserves its own explicit confirmation. Mandatory retyping is not necessary if the field is clearly presented beside the source and the user confirms it.
- Add a provider-specific disclosure and identity-document warning/acknowledgement before real use; decide provider terms, retention settings, consent language, and privacy-policy wording first.
- Keep first-page PDF scanning if its limitation stays clear. Do not rely on raw-byte name checks as PDF sanitization; my recommendation is to store only the rendered image initially.
- Remove the optional free-text reference field for the initial release.
- File ownership and response headers are good by inspection. The aggregate lock needs real PostgreSQL verification, and backup memory needs a smaller ceiling or a streaming/managed backup approach before large-scale use.

## C. Decisions

- **Part 1 — APPROVED WITH FIXES.** The requested notification and route fixes are in place by inspection. Tighten the login success/reset behavior and describe the lease timeout accurately before production use.
- **Part 2 — NOT APPROVED.** The manual-source bypass defeats the stated review invariant, and provider/privacy decisions remain open for sensitive identity scans. The reported tests and browser runs are useful evidence, but I did not reproduce them. PostgreSQL behavior, real provider handling, and real-device behavior remain unverified.

## D. Before showing this unit to anyone

1. Close the scan-to-manual bypass; require a scan-specific confirmed commit, and separately confirm the expiry date.
2. Decide the provider and identity-document policy; show the active provider and explicit warning before upload, and publish accurate retention/storage language.
3. Remove `reference` for the first release. Keep scanned PDFs as first-page image input, but defer storing original PDFs; impose browser-side PDF size/resource limits.
4. Add renewal history so a renewed document does not overwrite the old expiry and users can understand which reminder belonged to which term.
5. Add dashboard expiry indicators and document search, with filters for expired/soon/archived.
6. Consider circle sharing only after an explicit access model, since documents can expose identity and policy data.

I would refuse to add automatic saving of scan results, automatic renewal or payment actions, or document sharing by default. Those choices would undermine review, privacy, or clear ownership.
